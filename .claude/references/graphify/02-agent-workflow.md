# Graphify — How an Agent Should Use the Graph

Standalone reference for an LLM coding agent (e.g. Claude Code) working in
a repository that has a Graphify graph set up.

## The core habit: query before you grep

Once a graph exists, prefer it over blind exploration for any question
about how the codebase fits together:

- "What calls this function?" → `graphify explain "FunctionName"` or
  `graphify query "who calls FunctionName?"` instead of a repo-wide grep.
- "How does A relate to B?" → `graphify path "A" "B"` instead of manually
  opening files and tracing imports by hand.
- "What's the shape of this subsystem?" → read `GRAPH_REPORT.md` first
  (god nodes + communities), then drill into specific nodes.

This is faster, cheaper in tokens, and — because code edges are extracted
via deterministic AST parsing rather than approximate text search — often
more complete than a grep, which can miss indirect references, aliasing,
or cross-file call chains a regex won't catch.

Reading raw source files is still the right move once you've located the
specific file(s) you need to edit or inspect closely — the graph tells you
*where* to look and *how things connect*, not a substitute for reading the
actual code you're about to change.

## Reading edge confidence correctly

Every edge is tagged:

- `EXTRACTED` — explicit in the source. Trust these like you'd trust a
  compiler's own import resolution.
- `INFERRED` — Graphify resolved this relationship (e.g. matched a call
  site to a likely target across files). Treat as a strong lead, verify
  by opening the actual code before making a change that depends on it.
- `AMBIGUOUS` — Graphify couldn't confidently resolve it. Don't state this
  as fact; if it matters, open the source and check directly.

## Interpreting god nodes and communities

- A **god node** with very high degree is usually a hub — a router, a base
  class, a central config object, a shared utility. Changes there have
  wide blast radius; when asked to modify one, treat it as higher-risk and
  check its full neighbor list first.
- A **community** is Graphify's best guess at "this cluster of nodes is
  one subsystem." Use it to scope a task ("stay within the `auth`
  community") or to sanity-check whether a proposed change is crossing
  subsystem boundaries unexpectedly.

## When the graph might be stale

The graph reflects the state of the repo as of the last `extract`/`update`
run. If you've just made edits in the current session that haven't been
re-extracted yet, the graph won't know about them — rely on your own
recent edits and a targeted `grep`/file read for anything you changed in
this session, and treat the graph as ground truth for everything else.
Re-running `.claude/scripts/graphify.sh` refreshes it incrementally.

## Filing good answers back

If you work out something non-obvious using the graph — a subtle
connection, a root-cause trace, a confirmed answer to a recurring
question — it's worth recording with:

```
graphify save-result --question "Q" --answer "A" --nodes Foo Bar --outcome useful
```

Periodically, `graphify reflect` aggregates these into
`graphify-out/reflections/LESSONS.md` and tags graph nodes as
preferred/tentative/contested based on that accumulated experience, so
future `explain`/`query` calls surface a "Lesson:" hint. This is optional
but turns one-off investigations into durable, reusable context instead of
answers that only exist in one chat transcript.

## What not to do

- Don't treat `graph.json` as a replacement for tests or a compiler — it's
  a map, not a verifier. An edge existing (or not) is evidence, not proof.
- Don't assume the graph covers non-code content unless this repo's build
  was run in full mode (semantic extraction over docs/PDFs/images). A
  code-only build has no nodes for markdown docs, PDFs, or images — check
  `.graphify-mode` in `.claude/graph/` if unsure which mode was used.
- Don't edit anything under `graphify-out/` by hand — it's fully
  regenerated by `extract`/`update` and any manual edits will be lost.
